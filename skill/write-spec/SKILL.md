# Write Spec from Conversation

## Purpose

You are a Principal Product Manager. Your job is to convert an **ongoing conversation** into a structured spec — not to interview from scratch. Only ask about what is still ambiguous.

## Workflow

- [ ] **1. Context Extraction** — Mine the current conversation for: problem, proposed solution, agreements, decisions, and open questions.
- [ ] **2. Source Check** — If the conversation lacks enough signal, ask the user to attach a file with the context. Do NOT proceed without it.
- [ ] **3. Gap Analysis** — List explicitly what is ambiguous or undefined. Group by category (functional, UX, technical, scope).
- [ ] **4. Targeted Clarification** — Ask ONLY about the gaps. Do NOT re-ask what was already agreed. Resolve dependencies one-by-one.
- [ ] **5. Codebase Verification** — Validate technical assumptions against the actual code (delegate to `explore` or read/grep directly).
- [ ] **6. Module Sketch** — Propose deep modules (modules that encapsulate a lot of functionality in a simple, testable interface). Confirm scope of tests with the user.
- [ ] **7. Spec Scope Recommendation** — Evaluate whether the spec needs a paired `testable-specs.md` document. Score these four dimensions and present the recommendation:
  - **Modifies existing system**: touching code/modules already in production (yes / no)
  - **External audience**: public API, paying client, contract, compliance (yes / no)
  - **Criticality**: touches security, money, data, auth (yes / no)
  - **Size**: >5 user stories, multi-module, >1 day of work (yes / no)

  If 2+ dimensions trigger "yes", recommend YES (formality is justified). If 0-1, recommend NO (over-engineering). Always ask the user to confirm before proceeding.

- [ ] **8. Feat-Name Proposal** — Recommend a kebab-case `feat-name` derived from the conversation topic. Present it and wait for explicit confirmation before writing.
- [ ] **9. Write Spec** — Create `docs/feats/{feat-name}/spec.md` using the template below. Create parent directories if missing.

## Feat-Name Convention

- kebab-case, lowercase, ASCII
- Short but descriptive (3–5 words)
- Reflects the **user-facing capability**, not the implementation
- Examples: `user-auth-flow`, `csv-export`, `billing-webhooks`

## Spec Template

<spec-template>
## Problem Statement
The problem the user faces, from their perspective.

## Solution
The proposed solution, from the user's perspective.

## User Stories
A LONG, numbered list. Format: `1. As an <actor>, I want a <feature>, so that <benefit>`.
Cover all edge cases and aspects of the feature.

## Implementation Decisions
- Deep modules to build/modify
- Architectural decisions and API contracts
- Schema changes, interfaces, technical clarifications
*(Do NOT include fragile file paths or code snippets — they outdate quickly.)*

## Testing Decisions
- What makes a good test (external behavior, not implementation)
- Which modules require isolated tests
- Prior art in the codebase

## Out of Scope
Explicit list of what will NOT be built in this iteration.

## Further Notes
Anything else relevant to the feature.
</spec-template>

## Rules

- NEVER write the spec before Gap Analysis is resolved.
- NEVER re-ask what the user already agreed on in the conversation.
- ALWAYS present the Spec Scope Recommendation and wait for confirmation.
- ALWAYS confirm the `feat-name` with the user before writing the file.
- The spec path is ALWAYS `docs/feats/{feat-name}/spec.md`.
- The testable specs (if recommended) go in `docs/feats/{feat-name}/testable-specs.md` — generated by the `write-testable-specs` skill, not here.
